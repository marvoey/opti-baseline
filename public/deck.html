The Differentiating Reveal

The Shift: Slabs of Concrete vs. LEGO Bricks

Traditional Model: The Monolithic Page

A slab of concrete:

  • Headline, copy, case study, and form glued together
  • Every change requires cloning the entire page
  • High maintenance, link rot, governance drift
Optimizely Model: The Content Block

A LEGO brick with a smart luggage tag:

  • One specific message: A single headline, proof point, or action button
  • A smart taxonomy tag: "I belong to E-commerce" or "I belong to Packaged Foods"
  • Snaps into a single master template at runtime
TALK TRACK - EXPLAINING THE PARADIGM SHIFT:
"Up until now, the digital industry has forced marketing to think in Pages. A page is a monolithic slab of concrete: headline, body copy, case study, and form all glued together under one fixed URL. If you want to change one sentence for Aris Thorne at Unilever Foods, you have to clone the entire slab.

Optimizely breaks that slab into Content Blocks.

Think of a content block as an independent LEGO brick that has two things:
1. One specific message: A single headline, a single case study, or a single meeting button.
2. A smart label (taxonomy tag): A metadata tag that says: 'I belong to E-commerce' or 'I belong to Packaged Foods'.

You don't build pages anymore. Your copywriters author individual blocks once. Then, when a visitor arrives, our engine snaps the matching blocks together on the fly into a single layout."

Dynamic Delivery Fabric

Optimizely Graph: Sub-Second Resolution

query ResolveBrandSafeLimitlessPage(
  $visitorRole: String = "Ecommerce_VP",
  $visitorIndustry: String = "PackagedFoods",
  $visitorTier: String = "StrategicCustomer"
) {
  # 1. Hero resolves ONLY to visitor's role
  heroSlot: HeroBlock(where: { Persona: { eq: $visitorRole } }) {

    ClientQuote
  }
  # 3. Action resolves ONLY to verified entitlement tier
  actionSlot: ActionBlock(where: { Tier: { eq: $visitorTier } }) {
    LeadName
    CalendarUrl
  }
}

Privacy By Design

Content and Customer Identity Stay Separate

Making that work safely depends on one architectural rule: content never carries personal data.

Identity & Compliance Layer (ODP / CRM / MAP)
  Names · Emails · Consent · Activity History
    ↓ passes only anonymous tags, e.g. Industry: PersonalCare, Persona: Ecommerce_VP
Content Layer (Optimizely CMS + Graph) — Zero PII
  Email Templates · Hero Blocks · Proof Points · Action Blocks
    ↓ delivers the approved template / content snippet
Channel Merge — Web Session or Email Send
  Template tokens are filled with real identity only at this last step
Edge Caching

Content is cached globally for sub-50ms delivery — personal data should never sit behind that cache.

Right To Be Forgotten

Deletion requests apply cleanly to identity systems built for it, not content version history.

Least-Privilege Access

Editors and agency partners work in the CMS without ever touching customer records.

The personalization you just saw — resolved by account context, not identity — reaches web and email alike, while names and emails never leave your CRM, ODP, or marketing automation platform.
TALK TRACK:
"One question that always comes up here: doesn't personalizing content this precisely require the CMS to know who someone is? It doesn't — and that's by design.

Your identity platform — ODP, CRM, or marketing automation — is the only system that ever holds a name or email address. It passes Optimizely Graph nothing but anonymous tags like Industry and Persona. The CMS resolves content against those tags and hands back an approved snippet; identity and content are only combined at the very last step, inside your email platform or the visitor's own browser session.

That's how you get sub-second, highly personalized experiences across web and email without ever creating new GDPR or security exposure."
