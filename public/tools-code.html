What is a Tool?

An API route Mark can discover, call, and read. Two files. Let us read them.

Open with the problem: we pasted JSON by hand earlier. A Tool lets Mark fetch it itself. Everything in this deck is real code from app/api/opal on the shutterfly branch.
The idea

A Tool is an API with a manifest

Describe itDiscovery tells Mark what exists and what it takes.
Run itExecution does the work and returns JSON.
Use itMark picks it, fills the parameters, reads the result.
Three jobs, two files. Discovery is a GET that returns a manifest. Execution is a POST that does the work. Mark does the third job itself: choosing the tool and filling in arguments from the conversation.

Worth knowing

The description is a prompt

Mark reads the name and description to decide when to call your tool. Parameters tell it what to fill in. Write the description like a prompt, because it is one.

This is the one thing to take away from discovery. Vague descriptions mean the tool gets skipped or misused. Notice the parameter descriptions include examples such as 1042 and the holiday photo books URL.

Guardrails first

const SUB_PATHS = ['children', 'ancestors'];
const ID_PATTERN = /^[A-Za-z0-9-]{1,64}$/; // numeric id or GUID
const MAX_STRING = 512;

function str(value: unknown): string | undefined {
  return typeof value === 'string' && value.length <= MAX_STRING && value.trim() !== ''
    ? value.trim()
    : undefined;
}

// Opal expects a structured body it can show the model, so failures return 200.
function failure(error: string) {
  return Response.json({ success: false, error });
}

An ID pattern, an allow-list, a 512-character cap, and errors as data.

Three constants set the limits: allowed sub paths, an ID pattern for numeric IDs or GUIDs, and a maximum string length. The str helper returns a clean string or undefined. The failure helper returns success false with a message and a normal 200, so Mark can read the reason.

Read the request

export async function POST(request: NextRequest) {
  let body: Record<string, unknown>;
  try {
    const json: unknown = await request.json();
    body = json && typeof json === 'object' ? (json as Record<string, unknown>) : {};
  } catch {
    return failure('Request body must be valid JSON.');
  }

  // Opal may wrap tool arguments in a `parameters` object.
  const args =
    body.parameters && typeof body.parameters === 'object'
      ? (body.parameters as Record<string, unknown>)
      : body;

Bad JSON fails cleanly. Mark may wrap the arguments, so unwrap them.

POST handler. Parse the body inside a try. If it is not valid JSON, return a readable failure instead of throwing. Then handle the case where Opal nests the arguments under a parameters key.

Validate everything

  const contentId = str(args.content_id);
  const subPath = str(args.sub_path);
  const matchUrl = str(args.match_url);
  const expand = str(args.expand) ?? '*';
  const language = str(args.language);

  if (contentId && !ID_PATTERN.test(contentId)) return failure('content_id must be a numeric ID or GUID.');
  if (subPath && !SUB_PATHS.includes(subPath)) return failure("sub_path must be 'children' or 'ancestors'.");
  if (subPath && !contentId) return failure('sub_path requires content_id.');
  if (!contentId && !matchUrl) return failure('Provide content_id or match_url.');

Five values pulled out, four checks before anything runs.

Every argument goes through str. Expand defaults to a star so nested blocks come back in one call. Then four guards: content_id must match the pattern, sub_path must be children or ancestors, sub_path needs a content_id, and you must give a content_id or a match_url.

Patterns

Four habits worth copying

1Validate every input: ID pattern, allow-list, length cap.
2Stay read-only.
3Return errors as data: 200 with success false.
4Share one engine with your live API.
These are choices in the code, not Mark requirements. Read-only matters because the agent decides when to call it. Errors as data matters because the model can read the message and tell the user what went wrong.
